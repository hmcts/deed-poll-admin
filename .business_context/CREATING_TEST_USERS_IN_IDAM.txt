Creating Test Users in IDAMIntroductionRegistering users in IDAM is normally a two-step process.1. The user must register (or be registered) for the system, at which point the user will sent an email2. The user must open the email, click on the activation link and set their passwordOnly once the password is set do we create a user account. Note that registration can either be self-registration through idam-web-public, administrator-initiated through idam-user-dashboard/scripting or service-initiated through a system such as ref data. All of these registration types require the user to receive an email and activate their account.Since this two step process is inconvenient for automated testing the idam team have always provided testing-support endpoints which can create IDAM users in a single call, with their password already set. This document describes the new implementation of the idam-testing-support-api microservice which replaces the original implementation of testing-support which was available in the idam-api itself.Testing Principles* Test users should be created as part of your test, and be cleared down at the end of the test. To help with this the idam-testing-support-api will automatically remove test users after a period of time.* Test users can be recreated in the exact state that you need them (except for their create and modified dates). You can set the idam id to whatever value you need to, unless an existing IDAM user account exists in the environment with that id.* The IDAM team are not responsible for your test users and will not take manual action to maintain them. If your test user is broken or needs to be changed, please resolve this by using the testing support api to create a new test user, or update an existing one if you have to.* Test users should not need to be updated because they should be created for a single test, and should be short lived. It is possible to update users using the new testing support api but we would always recommend creating new users.* If you need longer lived users for demo purposes then they will need to be created/onboarded outside of idam-testing-support-api (see below)The idam-testing-support-api serviceThe new idam-testing-support-api service is available on all non-production environments, and allows for the creation and automatic cleanup of test users. You can view the AAT swagger definition here:https://idam-testing-support-api.aat.platform.hmcts.net/swagger-ui.htmlThe following postman collection contains example endpoints for creating test users and getting their latest emails:How to authenticate using client credentialsNote that the postman collection will automatically authenticate you using client credentials when you setup a postman environment with the details of your service.The idam-testing-support-api endpoints require OpenID "client_credentials" grants for their bearer authentication. You should use the client credentials of the service you are developing to make a /o/token call against idam-web-public to generate your token. The testing support api only requires you to have the "profile" and "roles" scopes in order to make calls.The access token is valid for a period of hours, so should only be generated once per testing session.curl -L -X POST 'https://idam-web-public.aat.platform.hmcts.net/o/token' \-H 'Content-Type: application/x-www-form-urlencoded' \--data-urlencode 'grant_type=client_credentials' \--data-urlencode 'client_id=PLACEHOLDER' \--data-urlencode 'client_secret=PLACEHOLDER' \--data-urlencode 'scope=profile roles'Note that the PLACEHOLDER values should be replaced with the appropriate values for your service.Note that you should reuse your access token for all related called to idam-testing-support-api, since the cleanup process is linked to the token. The token represents a batch of testing which will be cleaned up as one process.How to setup test users in IDAMThe POST /test/idam/users endpoint allows you to create an active IDAM user with whatever password and roles you want. You can also set the idam-id of the user to a specific value if you need the IDAM user record to be in sync with another system (i.e. ref data). A 400 BAD REQUEST will be returned if the password does not meet the normal IDAM requirements, or if any values are missing or incorrect. A 409 CONFLICT will be returned if the user id or email are already in use by another account.curl -L -X POST 'https://idam-testing-support-api.aat.platform.hmcts.net/test/idam/users' \-H 'Authorization: Bearer eyJ0eXAiOiJKV…' \-H 'Content-Type: application/json' \--data-raw '{    "password": "Pa$$w0rd",    "user": {        "id":"d8d8ad80-84d9-4416-95ea-bce1a6eb1247",        "email":"citizen-d8d8ad80-84d9-4416-95ea-bce1a6eb1247@test.aat",        "forename":"fn_d8d8ad80-84d9-4416-95ea-bce1a6eb1247",        "surname":"sn_d8d8ad80-84d9-4416-95ea-bce1a6eb1247",        "roleNames": [            "citizen"        ]    }}'For situations where you would prefer to update an existing IDAM account, or create it if it is missing then you can call the PUT /test/idam/users/{user-id} endpoint, which will create the user if they are not present, or update them if they are. Since this can create or update a user you need to provide all the necessary attributes for the user as though it were a normal POST /test/idam/users call. Do not update users that may be in use by other people. The IDAM team always advise that you create users on demand and do not use long-lived test accounts since such an approach can lead to fragile tests.How to get a test userThe GET /test/idam/users/:userId endpoint allows you to retrieve the details for a user.curl -L -X GET 'https://idam-testing-support-api.aat.platform.hmcts.net/test/idam/users/d8d8ad80-84d9-4416-95ea-bce1a6eb1247' \-H 'Authorization: Bearer eyJ0eXAiOiJKV1QiL…'You can also get users by email address with GET /test/idam/users?email={email}curl -L -X GET 'https://idam-testing-support-api.aat.platform.hmcts.net/test/idam/users?email=citizen-d8d8ad80-84d9-4416-95ea-bce1a6eb1247@test.aat' \-H 'Authorization: Bearer eyJ0eXAiOiJKV1QiL…'How to setup test users in ref dataBecause ref data duplicates values that are mastered in IDAM it is possible for the ref data database to contain data which is inconsistent with IDAM. Where this happens you should delete the IDAM user and recreate it with the same details that ref data already contains, including the id.If you are creating a new test user however it is better to create the user in IDAM first, since ref data will lookup the IDAM account when you create the user in ref data. If the account already exists then ref data will be able to set the ref data status of the account correctly, rather than having to wait for a sync process to run.NOTE That ref data assigns multiple IDAM roles to IDAM accounts, so do ensure that if you user testing-support to recreate a user that ref data originally created you include the same set of roles to ensure the user retains the same permissions.How to clear down test users after testingTest users created through idam-testing-support-api are automatically cleared down after a period of time. Note that the clear down process uses the bearer token as its key, so all users created using the same token will be cleared down as one batch.Environmentnew api cleanup strategyold api cleanup strategyAAT (and PRs)3h (after creation)15m (after creation)Demo90d (after creation)NoneITHC90d (after creation)NonePerftest1M (from last login)NoneSandbox (IDAM team only)2h (after creation)NonePreview (IDAM team only)2h (after creation)NoneHow to update a test user?Test users are not expected to be updated through testing support, since they should be created as required for the test, and removed once they are no longer needed. If you need to update an existing user you should request the user be deleted using DELETE /test/idam/users/:userid and then recreate them with the new values.Note that the deleting of test users in idam-testing-support-api is managed through a queue, so deleting may not be instantaneous.In some situations you can call the PUT /test/idam/users/{user-id} endpoint (see above), but the IDAM team do not recommend the use of long-lived test accounts and would advise teams to always create users on demand.Can I create test users without knowing my client credentials?Please discuss your requirements with the idam team.How to create service accountsService accounts (or system users) are managed in the https://github.com/hmcts/idam-access-config repository. You should not create system users using testing support endpoints. For more details please refer to IDAM Service Account Configuration FAQ.How to onboard long-lived users in non production environmentsOnboarding is a two step process which requires a user is first invited to use IDAM, and is then activated by clicking a link in an email. In testing environments idam-testing-support-api provides an endpoint which can give you the email body of the most recent email sent to a user. This allows teams to retrieve the activation link without having to look at real email addresses.The invitation of users is normally handled by teams other than IDAM, who have developed scripts to handle the process. If you require one or more long lived users in a test environment you should first consider how you plan to onboard users in the production environment and contact the relevant team for advice (i.e. XUI, ref data, CFT L2 etc.)Having registered a user you can retrieve the most recent notification (email) for a given email address by calling GET /test/idam/notifications/latest/:emailAddress and then extract the activation link from the email body. See "How to get emails for test users" below for more details.How to get emails for test usersIDAM uses the notifications.gov.uk service to send emails. In lower environments we should be using notify with TEST api keys that only pretend to send emails. To accomodate testing where you may need to get the email for a test user in a lower environment the idam-testing-support-api provides an endpoint that can be used to get the latest notification (email) for a user based on their email address. Since this is accessing the notification from the notifications service this does not have to be a real email address backed by a mail server.curl -L -X GET 'https://idam-testing-support-api.aat.platform.hmcts.net/test/idam/notifications/latest/citizen-d8d8ad80-84d9-4416-95ea-bce1a6eb1247@test.aat' \-H 'Authorization: Bearer eyJ0eXAiOiJKV1…'This endpoint will work for any email that is sent from IDAM not just activations, for example "forgot password". You can only retrieve the single most recent email. The response is a Notification object as per the notify api: https://docs.notifications.service.gov.uk/java.html#get-the-status-of-one-message-responseWhat does this replaceThe original testing-support endpoints were part of the idam-api implementation which were feature flagged as active in non-prod environments. These endpoints will continue to work for now, but will call the newer idam-testing-support-api to fulfil their calls in the future.The old approach is documented here:Old Way of Creating Test Users in IDAMWhy is this changingThe original testing support implementation did not make it easy to clean up test data at the end of testing. This led to the build up of large numbers of inactive test accounts in the AAT environment which would periodically degrade the performance of the environment. Manually cleaning up these inactive accounts was time consuming and difficult to do while the environment was in use.
